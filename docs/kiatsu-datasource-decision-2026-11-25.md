# 気圧モジュールのデータ源選定（2026-11-25）

対象: `src/modules/kiatsu/`（頭痛ーる zutool.jp の非公式 API に依存する気圧投稿モジュール）
結論の種別: 設計判断（実装前の文書化）

---

## 1. 何が起きたか

2026-11-25 16:16 JST、zutool.jp のフロント JS が更新され、`/api/getweatherstatus/{地点ID}` に `X-Zutool-Weather: <署名付きトークン>` が必須になった。トークンはトップページ HTML の `window.ZUTOOL_WEATHER_TOKEN` に `<有効期限Unix秒>.<署名>` の形で埋め込まれ、有効期限は約30分。ヘッダー無し・ダミー値はどちらも 403、UA/Referer/Cookie をブラウザ相当にしても 403。

トークンを取得して付ける「回避」は方針として却下した。自動アクセス防止を意図的に抜ける行為であり、同じ仕組みが次の変更で一撃で塞がれるため。したがって選択肢は「機能を消す」か「別データ源へ移す」に限られる。

なお `getpainstatus`（都道府県別の体調分布）と `getweatherpoint`（地名検索）は現在もトークン不要で応答する。ただし前者は気圧ではなく自己申告の体調比率であり、気圧機能の代替にはならない。

---

## 2. 移行先候補の実測精度

地点は群馬県高崎市（36.32N / 139.00E）、比較基準はアメダス前橋（42251、標高112m）。期間は 2026-11-22 21:00〜11-25 19:00 の 71 時間。実況の気圧振幅は 27.7 hPa、ΔP3h の最小は −6.2 hPa で、平穏な期間だけを拾った検定ではない（ERA5 の 11 月平年 1.27 に対し検証窓は平均 1.68）。

### 2.1 使える数字と、使えない数字

| 指標 | 公表値 | 監査後の代表値 | 注記 |
|---|---|---|---|
| ΔP3h の MAE | 0.341 hPa | **0.36〜0.42 hPa** | 分母を63点に揃え、公開ラグ2〜3時間を課した範囲 |
| ΔP3h の符号一致率 | 93.7%（母数63） | 91.2%（全68点） | フィルタ無しの値は当初未記載 |
| ΔP6h / ΔP12h の MAE | 0.429 / 0.437 | 変更なし | 再計算で一致 |
| 有効標本数 | 68 時間 | 約 24 | 誤差の lag-1 自己相関 +0.473、ΔP の 44% が別ラン由来 |
| 3日を単位とした 95%CI | 未算出 | [0.06, 0.64]（0.5 を含む） | 日別 MAE は 0.246 / 0.325 / 0.475 と悪化 |

再計算は 60 項目中 59 項目が表示桁で一致した。数値の計算に作為は無く、修正が必要だったのはラベルである。p50 だけは 0.30 と記載されていたが正しくは 0.25 だった。

### 2.2 モデルと標高

- 高崎座標では `best_match` が `jma_msm`（気象庁 MSM、5km、毎時）と一致する。ただし約85時間までで、末端では別モデルへ継がれ最大 3.0 hPa 乖離する。`models=jma_msm` を明示すれば 400 で検知できるが、`best_match` の応答にモデル識別子は無いため、暗黙の切替は検知できない。**ピン留めは必須**。
- `elevation` を指定しないと `surface_pressure` に +3.67 hPa の系統バイアスが出る（DEM 標高 82m、前橋 112m）。`pressure_msl` は標高に依存しない。
- 当初「ΔP は標高に影響されない」と書いたが誤り。MAE が偶然相殺していただけで、ΔP12h の値は最大 0.30 hPa 動く。

### 2.3 精度の判定

「ΔP3h の誤差は 0.5 hPa を下回る」という結論は支持できる。ただし根拠の強さは当初の想定より弱い。1地点・3日間・11ランであり、日別に見ると最終日は 0.475 で合格線の直上にある。閾値を −1.0 hPa 帯に置くと誤差 0.5 hPa 超が 19% 現れ判定が振れるので、閾値は −2.0 hPa 以深に置くのが妥当である（−2.0 以深で誤差 2.0 hPa 超は 68 時間中 0 件）。

## 3. 頭痛ーるの「警戒レベル」は再現できない

`/about` の FAQ に、レベルが「1日を4つの時間帯（3〜9時、9〜15時、15〜21時、21〜翌3時）に分け、時間帯ごとの気圧低下量の**年間平均値**を基準に表示している」と明記されている。式そのものは非公開で、当の API はもう応答しない。

つまり 0〜4 のレベルは地点ごと・時間帯ごとの年間統計を基準にした相対量である。3日間の測定では再現できず、同じ番号を別の意味で配ることになる。利用者は zutool の意味での「レベル2」を知っており、移行後にこちらが出す「レベル2」を検証する手段は無い。

したがって 0〜4 の語彙は移植しない。代わりに「3時間で −2.3 hPa 下がる見込み」という検証可能な事実を出す。年間統計を再現してレベルを維持する案は技術的には可能だが、地点ごとに1年分の履歴と継続的な再計算が要る。

---

## 4. 本当の弱点はサンプリングだった

実況で警戒域に入ったエピソードは 68 時間中 4 本、長さは 3 / 9 / 7 / 1 時間。現行の投稿は12時間間隔の点サンプルである。

| 投稿間隔 | エピソード捕捉（位相を全探索） |
|---|---|
| 3h | 最良 4/4・最悪 3/4 |
| 6h | 最良 4/4・最悪 2/4 |
| **12h（現行）** | 最良 3/4・最悪 0/4 |
| 24h | 最良 2/4・最悪 0/4 |

MAE を 0.34 から 0.20 に改善しても、この捕捉率は変わらない。精度だけを見て移行可否を決めると、製品の主要な故障モードを見落とす。一方で閾値を浅くして捕捉率を上げると投稿量が増える（ERA5 の6年分では ΔP3h ≤ −2.0 が 11 月に月 25.4 回、冬に 27.8 回）。頻度の上限設計が必須である。

## 5. 規約とライセンス

- zutool の利用規約に自動アクセス・スクレイピング・API 利用の禁止明文は無い（`/rules`・`/privacy-policy`・`/app/tos.html` の全文と `robots.txt` を確認）。ただし第3条2が「転載・改変・複製・頒布ならびに公衆送信」を禁じており、取得値を Misskey に投稿する行為は公衆送信に当たり得る。現状の「zutool 値を投稿」が規約上は最も不利で、移行は改善になる。
- Open-Meteo の無料枠は**非商用限定**（CC-BY 4.0、10,000 calls/日）。terms は「広告やサブスクを表示するサイト/アプリ」を商用の例に挙げる。投稿先インスタンスの広告有無を確認する必要がある（未確認）。
- CC-BY 4.0 の帰属表示は義務であり、任意の装飾ではない。画像フッターと投稿文の両方に出す。

## 6. パネル討論の結論

設計担当と反証担当の2名で、独立回答→相互批判の2ラウンドを行った。当初は「Open-Meteo へ移行しレベルを自前定義で残す」案と「データ源は移すがレベルと12時間サンプリングを捨てる」案で対立し、相互批判を経て後者に収束した。設計担当が譲った論点は「レベルの語彙は移植できず、検証手段が消える」の1点である。

### 合意した点

1. エラー通知ループを最優先で止める（選択肢に依存しない）。`handleError()` は `errorCount` を成功時にしかリセットしないため、再開直後の1エラーで即再停止し、「一時停止／再開」を1時間ごとに投稿し続ける。`index.ts:112` が唯一のリセット箇所。
2. `models=jma_msm` を固定し `elevation` を明示する。地平外は `unknown` として投稿しない。
3. レベル 0〜4 は廃止し、ΔP の事実文に置き換える。
4. 画像は残す。ただし level 列を ΔP 列に変え、MSM の地平（現在から約67時間）を超える末尾は欠測表示にする。3日表示は末尾約5時間が空く。
5. 精度は「条件付きで足りる」。断定はできない。

### 対立が残った点と裁定

- 「予報 ΔP3h が −2.0 を初回突破した時刻に投稿する」案は、MSM が3時間ごとに更新されるため突破時刻が動き、冪等キーが無いと再投稿や取り消し漏れを起こす。現時点の ΔP3h で判定し、ヒステリシスと1日あたりの投稿上限を併用するのが正しい。
- 閾値を −4.0 にすると ERA5 で月 3.7 回まで減り、捕捉率が犠牲になる。−2.0 を採るなら頻度上限が必須で、閾値 −2.0、ヒステリシス 0.5 hPa、1日1回上限を推奨する。

## 7. 推奨案

Open-Meteo（`models=jma_msm` 固定）へ移行し、レベル語彙と12時間点サンプルを捨てる。投稿文は検証可能な事実文にする。

```
気圧が下がってきています（3時間で -2.3 hPa、前橋付近の予報）
source: Open-Meteo (JMA MSM) / CC-BY 4.0
```

作業は次の順で分ける。

1. 当日の独立した変更として、`registry.ts:18,72` から気圧モジュールを外して停止する（`enabled` キーは存在せず、追加すると schema 変更になるため、まずは登録解除で止める）。エラー通知ループの停止を兼ねる。
2. 配線せず純粋な追加として、Open-Meteo アダプタ（`models=jma_msm`、`elevation` 明示、`past_days=1` で日界の ΔP を確保）と ΔP 判定（純粋関数＋ヒステリシス）、テストを足す。既存の `weather/api.ts:167-190` の `getJson` + `searchParams` の形を踏襲する。
3. 配線として、`kiatsu/index.ts:75-104` を差し替え、設定を `locationCode` から緯度経度＋標高＋`enabled` へ移行する（`schema.ts:195-203`、`schema.ts:665-666`、`example.config.toml:202-210`、`config.toml:166-174`、`info/format.ts:279-295`）。
4. 描画として、`render-kiatsu.ts` のフッターと level 列のみ変更する（`6-24`、`229-230`、`333-349`、`443`）。
5. 文書として、本ファイルに閾値の根拠と継ぎ目の実測を追記し、`torisetu-fork.md:16` の利用者向け説明を更新する。

テストは3層に分ける。決定的な定義テスト（単調性、境界、`NaN` は投稿しない、ヒステリシス遷移）、凍結フィクスチャによる回帰、頻度不変量（30日リプレイで投稿回数が範囲内）。実況との突合は月次レポートとして分離し、CI の assertion にしない（気象で落ちるテストは必ず無効化される）。

### 削除を選ぶ場合

`src/modules/kiatsu/` の 2 ファイル 668 行を削除し、上記の参照 10 箇所を片付ける。テストは存在しないため壊れるものは無い。エラー通知ループも同時に消える。コードは git 履歴に残るので復活は可能だが、復活時に再検証が必要になる。

### 撤退条件

次のいずれかが起きたら削除に切り替える。4季節の再評価で ΔP3h の MAE が 0.5 hPa を1季節でも超える、`models=jma_msm` が 400/404 を返す、terms から無料枠や CC-BY が消える、投稿先インスタンスが広告や課金を掲載している、移行後90日でメンション応答が実質ゼロ。
